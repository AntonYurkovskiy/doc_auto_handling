# Общие правила для задач OCR-плана

Этот файл читается первым в каждой задаче `docs/ocr_tasks/prompts/T*.md`.
Ты выполняешь **одну атомарную задачу** в неинтерактивной сессии (`claude -p` или `devin -p`).
Человека рядом нет, и спросить его нельзя. Мелкие развилки решай сам и записывай решения.
На критичных развилках останавливайся и записывай вопрос в журнал (см. ниже).

## 1. Что прочитать перед началом

1. `docs/ocr_tasks/CONTEXT.md` — факты о локальном окружении, данных и текущем OCR-коде
   (создаёт T00).
2. `docs/ocr_tasks/PROGRESS.md` — журнал: что уже сделано, цифры, решения предыдущих задач.
3. `docs/ocr_tasks/DECISIONS.md` — ответы человека. **Они важнее плана и этого файла.**
4. `docs/ocr_dates_plan.md` — план подхода, источник истины по методу. По необходимости:
   `ocr_dates_guide.md`, `docs/class_vs_ocr.md` (классификация вместо OCR),
   `docs/base_logic.md` (доменная модель).

Читай то, что нужно задаче. Не надо перечитывать весь репозиторий.

## 2. Среда

- Windows. Репозиторий — `E:\projects\doc_auto_handling\doc_auto_handling`.
  Команды выполняй через Bash-инструмент (Git Bash), пути пиши с прямыми слешами.
- Python приложения — `.venv/Scripts/python`. Для обучения — `.venv-train/Scripts/python`,
  если T05 уже выполнена (см. CONTEXT.md).
- Раннер выставляет `PYTHONUTF8=1`. Если запускаешь Python иначе — выставь сам, иначе
  кириллица в выводе ломается на cp1251.
- GPU — GTX 1050 на 4 ГБ (Pascal, sm_61). Работает только FP32: AMP и bf16 не использовать.
  На диске C: мало места, поэтому тяжёлое (кэши HF и torch, модели) держи на E:.
- Одна команда Bash живёт не дольше 10 минут. Долгие процессы запускай так:
  - с флагом `--max-minutes 9`, чекпоинтом и возобновлением;
  - или в фоне, с записью в лог и опросом лога.

## 3. Данные

- **Только чтение:** `data/historical/**` и каталоги сканов из колонки `voucher_scan_path`.
  Там ничего не создавать, не переименовывать и не удалять.
- **Производные артефакты** — только в `data/ocr/`. Пути бери из `ocr_lab/paths.py`
  (он появляется в T02; до него — из CONTEXT.md).
- **Реальные данные не коммитить.** Сюда относятся сканы, кропы, CSV, отчёты с построчными
  значениями и веса моделей. В git идут только:
  - код;
  - тесты на синтетике;
  - JSON-макеты боксов;
  - документы с агрегированными цифрами.
- **Не выводить лишнего** ни в консоль, ни в журнал.
  - Можно: агрегаты, `scan_id`, номера ваучеров.
  - Нельзя: имена судов и агентов, тексты писем, суммы.
  - В сообщениях об ошибках пиши `scan_id`, а не данные (урок F-230 из справочника моделей).
- **Картинки** смотри инструментом Read (PNG/JPG). Правила для листов:
  - длинная сторона ≤ 2000 px, не больше 100 кропов на лист;
  - у каждого кропа видимая подпись-индекс, рядом с листом — CSV «индекс → scan_id»;
  - если `DECISIONS.md` запрещает показывать сканы модели, листы готовь для человека,
    сам их не смотри, и завершай задачу со статусом «частично».

## 4. Код

- **Рантайм** (то, что импортирует приложение) — пакет `app/ocr/`.
  - Только CPU и лёгкие зависимости: numpy, opencv-python-headless, pypdfium2, Pillow,
    onnxruntime.
  - **torch в `app/ocr/` не импортировать.**
- **Исследования и обучение** — пакет `ocr_lab/`, CLI через `python -m ocr_lab.<модуль>`.
  Здесь torch можно.
- **Тесты** — в `tests/ocr/`, в каталоге должен быть `__init__.py`.
  - Только синтетические данные.
  - Пути через `tmp_path` и `pathlib`, без жёстких `/tmp` и `C:\` (урок F-242).
- **Имена подполей** одинаковы во всех задачах.
  - Строки: `left_base` (Выход из базы), `arrived_base` (Приход в базу),
    `started_work` (Начало работ), `finished_work` (Окончание работ).
  - Части строки: `day`, `month`, `hour`, `minute`. Подполе записывается как
    `<строка>.<часть>`, например `left_base.hour`.
  - Номер ваучера — `voucher_number`.
  - Хронология строк: `left_base ≤ started_work ≤ finished_work ≤ arrived_base`.
- **Стиль** — как в репозитории:
  - `from __future__ import annotations`, аннотации типов;
  - докстринги и комментарии по-русски;
  - ruff с длиной строки 100.
- **Зависимости:**
  - рантайм — в `requirements.txt`, с `==`;
  - обучение — в `requirements-train.txt`;
  - каждую новую зависимость обоснуй в журнале.
- **Модули вне задачи не трогать.** Если без правки не обойтись — сделай минимальную и
  запиши её в журнал.

## 5. Проверки перед завершением

```bash
.venv/Scripts/python -m ruff check .
.venv/Scripts/python -m mypy app
.venv/Scripts/python -m pytest -q
```

Всё должно быть зелёным. Падения, которые были до тебя, перечислены в CONTEXT.md
(«Базовые проверки»). Их не чини, но и новых не добавляй. Кроме того, выполни проверки
из раздела задачи «Критерии приёмки».

## 6. Git

- Работай в текущей ветке: её выбрал человек.
- Не переключай ветки. Запрещены `push`, `rebase`, `reset --hard`, `clean`, `checkout -- <файл>`.
- В конце сделай **один коммит**:
  - `git add <конкретные файлы>`, а не `-A`;
  - сообщение по-русски: `OCR T06: <что сделано>`;
  - перед коммитом проверь `git status`: в индексе не должно быть данных.

## 7. Решения и блокеры

- **Мелкая развилка** — выбери простой разумный вариант и запиши его в «Решения без человека».
- **Критичная развилка** (данные, архитектура, необратимое) или нехватка входов:
  1. не обходи её;
  2. запиши вопрос в «Вопросы к человеку»;
  3. сделай то, что можно без ответа;
  4. заверши со статусом «частично» или «заблокировано».
- **Результат хуже ожидаемого** — не подгоняй. Честно запиши цифры и гипотезы.

## 8. Журнал (обязательно)

Добавь в конец `docs/ocr_tasks/PROGRESS.md` раздел:

```markdown
## T06 — <название задачи> (<дата>)
- Статус: готово | частично | заблокировано
- Сделано: <3–7 пунктов: файлы, модули, артефакты в data/ocr/>
- Цифры: <ключевые метрики и счётчики>
- Решения без человека: <что выбрал и почему>
- Вопросы к человеку: <нет | список>
- Для следующих задач: <интерфейсы, пути, подводные камни>
```

Строку `- Статус:` пиши ровно так: по ней раннер проверяет зависимости.
Если узнал о среде что-то новое и важное, дополни `CONTEXT.md`.
Последнее сообщение сессии — тот же итог в 3–6 строках.
