# T19. Совместный декодер (`app/ocr/decoder.py`) — ядро

## Зачем

Рычаг №2 плана. Не читать каждое подполе отдельно, а найти **самую вероятную запись
ваучера целиком**, которая не противоречит правилам. Факты из данных (план,
«Что нашлось»; уточнения — в отчётах T02 и T04 и в `DECISIONS.md` после точки H1):

- Порядок `Выход ≤ Начало ≤ Окончание ≤ Приход` выполняется в 98,6 %. Нарушения — в
  основном ошибки выгрузки. Это **жёсткое** правило.
- День почти всегда записан 4 раза одинаково: это 4 голоса за одно значение. Через полночь
  переходят 2,2 % ваучеров (+1 день).
- Минуты кратны 10 в 99,8 %: 6 значений из 3111 кратны только 5. Это **мягкий** приор,
  не запрет.
- 99 % ваучеров укладываются в 5,3 ч от выхода до прихода.
- Время из заявки — слабый приор: медиана отклонения +4 ч, в ±3 ч попадает 43 %,
  99-й перцентиль — +6 суток. **Жёсткого окна нет.** Нынешняя сетка ±3 суток в
  `candidate_datetimes` отрезает хвост — её заменит этот декодер (удаление будет в T26).
- `24:00` — допустимая запись конца суток, если минуты 00 (см. `ocr_dates_guide.md`).
  Как её пишут на самом деле, выяснила T04.

## Модель

Запись — четыре datetime (`left_base`, `started_work`, `finished_work`, `arrived_base`)
с флагами `hour24`. Её оценка — сумма логарифмов:

1. **Картинка.** `Σ_подполя w_part · log P_img(значение)` из откалиброванных
   распределений (`app/ocr/runtime.py`, T18). Пропущенное подполе (кроп не получился)
   даёт равномерное распределение.
2. **Даты.** Базовая дата B — дата выхода. Для строк в хронологическом порядке смещения
   `o ∈ {0, 1}` не убывают. День и месяц строки r сверяются с `B + o_r`; для `24:00`
   день на бланке — `B + o_r`, а время — 00:00 следующих суток. Год берётся из контекста
   (имя файла или печать); отдельно обработай переход через Новый год. Переход месяца
   (31 → 1) должен получаться сам, через календарную арифметику.
3. **Приоры** (из `train`, скриптом `ocr_lab/fit_decoder_priors.py` в
   `data/ocr/models/decoder_priors_v0.json`):
   - распределение минут, сглаженное;
   - часы по строкам;
   - длительности `Начало − Выход`, `Окончание − Начало`, `Приход − Окончание` —
     тяжелохвостые, эмпирические с полом; по виду работ, если данных хватает, иначе общие;
   - частоты шаблонов смещений дней;
   - отклонение `Начало − время заявки` — тяжелохвостое, с полом, **без окна**.
4. **Жёсткие правила:** цепочка по времени; час 24 только с минутами 00; дата валидна.

Веса (`w_part` и множители приоров) подбери на `val` по откалиброванным предсказаниям
`digits_v0` из T18:
максимизируй лог-правдоподобие истинной записи при softmax по перечисленным кандидатам
или точность top-1 на небольшой сетке. Запиши их в тот же JSON.

## Поиск

- Кандидаты подполя — top-k (например, часы — 4, минуты — 3, дни — объединение top-3
  по строкам, месяцы — 2), плюс отсечение по минимальной вероятности.
- Оценка раскладывается на унарные члены строк и парные члены соседних строк цепочки.
  Поэтому подходит точное k-лучшее динамическое программирование или beam по цепочке.
  Допустим и векторизованный полный перебор, если он укладывается во время.
- Точность поиска проверь тестом: на маленьких входах результат совпадает с полным перебором.
- Время: меньше 30 мс на ваучер на CPU. Только numpy, без torch.

## Выход

`decode(inputs, context) -> DecodeResult`:
- top-N записей с нормированными вероятностями (softmax по перечисленным);
- `confidence = p(top1)` и `margin`;
- маргинальные top-3 по каждой строке — для кнопок в UI (T27);
- флаги: какие правила сработали, какие подполя отсутствовали.

Контракт зафиксируй dataclass-ами; `inputs` — в формате `runtime.predict_digits`.

## Тесты: `tests/ocr/test_decoder.py`, синтетические распределения

1. Top-1 картинки нарушает цепочку, второй вариант — нет: декодер выбирает второй.
2. Переход через полночь: выход 23:40 дня 5, окончание 00:30 дня 6.
3. Переход месяца 31.01 → 01.02 и Нового года 31.12 → 01.01.
4. `24:00` с минутами 00 допустимо; `24:10` — нет.
5. Минуты `45` при очень уверенной картинке принимаются, при неуверенной побеждает `40`
   или `50`.
6. Время заявки на +6 суток запись не отбрасывает, а только слегка штрафует.
7. Пропущенное подполе: результат есть, `confidence` ниже.
8. Совпадение с полным перебором на малом входе.
9. Время работы.

## Оценка

- Прогон по `val`: откалиброванные предсказания `digits_v0` → декодер → JSONL в формате T13 →
  `ocr_lab.evaluate`.
- Сравни точность записи целиком «top-1 по полям» против «декодер», а также ошибку
  в минутах.
- `test` — один прогон в конце, только для отчёта.

## Критерии приёмки

- Декодер повышает точность записи целиком на `val`. Если нет — это разобрано в журнале.
- Кривая «покрытие — точность» по `confidence` на `val` построена (`ocr_lab.evaluate`).
- Проверки из `_common.md` зелёные; `app/ocr/decoder.py` зависит только от numpy
  и stdlib.

## Если не получается

Если после двух честных попыток декодер не даёт прироста или ломается на граничных
случаях, опиши гипотезы в журнале и заверши со статусом «частично». По справочнику
моделей следующая ступень — эскалация: этот же промпт на `--effort max`, затем Devin
`claude-fable-5-1-high`.
