# T02. Манифест датасета («замороженная истина») и сплит по времени

## Зачем

Всем следующим задачам нужна одна таблица: скан → буксир → значения по подполям → сплит.
Истина в выгрузке шумная: в `docs/ocr_dates_plan.md` (приложение) 4 из 11 нарушений порядка
оказались ошибками выгрузки. Поэтому поправки хранятся отдельно и применяются явно.

## Что сделать

### 1. Пакет `ocr_lab`

- `ocr_lab/__init__.py`.
- `ocr_lab/paths.py` — единственное место с путями.
  - Корень репозитория, `DATASET_CSV` (по умолчанию из CONTEXT.md; переопределяется
    переменной `OCR_DATASET_CSV`).
  - `WORK_DIR = data/ocr` (переменная `OCR_WORK_DIR`) и подкаталоги: `pages`, `layouts`,
    `crops`, `sheets`, `review`, `labels`, `models`, `reports`, `logs`.
  - `CORRECTIONS_CSV = data/ocr/truth_corrections.csv`.
  - Функции создают каталоги по требованию.
  - Если переменные `HF_HOME` и `TORCH_HOME` не заданы, выставь их в каталог на E:
    (путь — из CONTEXT.md). Делай это до импорта transformers и torch и отдельной
    функцией, а не при импорте модуля.

### 2. Поправки истины: `data/ocr/truth_corrections.csv`

Колонки: `scan_id, field, export_value, corrected_value, status, source, note`.
- `status`: `confirmed`, `proposed` или `rejected`;
- `field`: одна из четырёх строк или `voucher_number`.

Засей файл четырьмя проверенными случаями из приложения плана (`status=confirmed`,
`source=ocr_dates_plan`):

| Ваучер | Поле | Было в выгрузке | Правильно |
|---|---|---|---|
| 1k (2025) | `arrived_base` | 05.01 12:50 | 05.01 13:40 |
| 179k (2025) | `started_work` | 27.07 07:30 | 24.07 07:30 |
| 179k (2025) | `finished_work` | 27.07 08:10 | 24.07 08:10 |
| 326p (2025) | `started_work` | 21.12 21:40 | 20.12 21:40 |
| 326p (2025) | `finished_work` | 21.12 21:50 | 20.12 21:50 |
| 64p (2026) | `arrived_base` | 11.02 15:30 | 11.02 16:30 |
| 64p (2026) | `finished_work` | 11.02 16:30 | 11.02 15:30 |

Если файл уже есть, не перезаписывай его. Только добавь недостающие строки: T04 и T21
тоже пишут в этот файл.

### 3. Сборка манифеста

`ocr_lab/manifest.py`, запуск `python -m ocr_lab.manifest build`.
Результат — `data/ocr/manifest.csv`.

**Строки.** Одна строка на уникальный скан.
- Убери дубли: план говорит о 779 строках на 774 скана. Если у дублей расходится истина —
  оставь одну строку, поставь флаг и выведи список.
- Убери ваучеры не Коммунара и не Пионера (по плану их 2) и перечисли их в отчёте.
- `scan_id` — стабильный и безопасный для файловой системы: `<год>_<имя файла без
  расширения>`, где `(2)` заменено на `_2`. Пример: `2025_156k_2`.

**Колонки.**
- **Ваучер:** `tug_code` (`k`/`p`), `year`, `voucher_number` (int), `voucher_file`,
  `scan_path`, `scan_exists`, `ext`, `application_file`.
- **Работа:** `work_type_raw`, `work_type` (через `app.services.calculation.normalize_work_type`),
  `agent_group` (A/B/C по `app.config.agent_group`, без имени агента).
- **Время из заявки:** `app_dt` — колонка из CONTEXT.md; если её нет, оставь пусто и
  запиши вопрос.
- **Истина по строкам.** Для каждой строки `r` из `left_base`, `arrived_base`,
  `started_work`, `finished_work`:
  - `r_dt` в ISO — это время после поправок;
  - `r_day`, `r_month`, `r_year`, `r_hour`, `r_minute` (int), причём `hour` может быть 24
    (см. ниже).
  - Источник: `left_base` ← `base_departure`, `arrived_base` ← `base_arrival`,
    `started_work` ← `work_start`, `finished_work` ← `work_end`.
- **Флаги:**
  - `truth_corrected` — какие поля поправлены;
  - `chain_ok` — выполнено `left ≤ start ≤ end ≤ arrived`; плюс `chain_violation` —
    что именно нарушено;
  - `crosses_midnight`;
  - `minutes_mult10`;
  - `has_hour24`.
- **Пары:** `pair_id` — ваучеры обоих буксиров по одной работе.
  Работа = тот же `application_file` + тот же нормализованный вид работ + выход из базы
  в пределах 6 часов. Проверь себя: по плану пар около 195, и в ~131 из них (67 %) все
  времена совпадают.
- **Сплит:** `split` по дате `left_base_dt`:
  - `train` — до 2026-03-31 включительно;
  - `val` — с 2026-04-01 по 2026-05-31;
  - `test` — с 2026-06-01.

  Границы задай константами. Если `DECISIONS.md` задаёт другие — бери их.
  Оба ваучера пары должны быть в одном сплите.

**Полночь.** Если в выгрузке встречается `24:00`, сохрани `hour=24`, `minute=0` в
подполях и `has_hour24=True`, а в `r_dt` запиши 00:00 следующих суток. Ничего не теряй:
ноль часов и 24 часа — разные написания на бланке. В плане сказано, что `00:00` в истине
нет, — проверь это.

### 4. Отчёт: `data/ocr/reports/manifest_report.md`

Только агрегаты:
- счётчики буксир × год × сплит;
- удалённые дубли и сканы третьего буксира (`scan_id`);
- отсутствующие файлы сканов;
- нарушения цепочки до и после поправок (`scan_id` и вид нарушения);
- доля переходов через полночь (в плане 2,2 %);
- доля минут, кратных 10 (в плане 99,8 %), и список некратных значений;
- гистограмма часов по строкам;
- распределение `arrived − left` (в плане 99 % ≤ 5,3 ч);
- статистика пар.

Цифры сравни с планом и отметь расхождения.

### 5. Тесты: `tests/ocr/test_manifest.py`

Нужен `tests/ocr/__init__.py`. Синтетический CSV в `tmp_path` должен покрывать:
дубли, третий буксир, `24:00`, переход через полночь, применение поправки, сплит,
формирование пары.

## Критерии приёмки

- `python -m ocr_lab.manifest build` отрабатывает на реальных данных. Повторный запуск даёт
  тот же результат (идемпотентен).
- Если число сканов не 774, в журнале есть объяснение.
- `manifest.csv`, поправки и отчёт лежат в `data/ocr/` и не попадают в git.
- Проверки из `_common.md` зелёные.
